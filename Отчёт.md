# Отчёт по домашнему заданию: клиент-серверное приложение Cinema

## 1. Доменная область

Cinema — учебное приложение онлайн-кинотеатра.

Приложение предназначено для ведения каталога фильмов
и просмотра видео в браузере по прямой HTTP/HTTPS-ссылке.

Пользователь может:

- создать запись о фильме;
- просмотреть каталог;
- получить информацию об отдельном фильме;
- изменить данные фильма;
- удалить фильм;
- открыть видео во встроенном браузерном плеере.

Область реализации ограничена каталогом и воспроизведением
внешних видеоисточников.

Регистрация, подписки, платежи, загрузка видео и перекодирование
в текущую версию не входят.

## 2. Стек реализации

### Backend

- Язык Go.
- HTTP-сервер и маршрутизация из стандартной библиотеки net/http.
- Драйвер PostgreSQL pgx.
- JSON для представления данных API.
- log/slog для структурированного логирования.

### Frontend

- HTML.
- CSS.
- JavaScript.
- Fetch API для обращения к backend.
- HTML-элемент video для воспроизведения.

### Хранение данных и окружение

- PostgreSQL 17.
- SQL-миграции.
- Docker для сборки образа.
- Docker Compose для локального запуска.
- Go Modules для управления зависимостями.

Frontend и backend взаимодействуют по HTTP/REST.
Локальный HTTP-сервер совместим с HTTP/1.1.

## 3. Основные сущности

### Фильм — Movie

Основная доменная сущность приложения.

Поля:

- id — уникальный идентификатор;
- title — название;
- description — описание;
- release_year — год выпуска;
- video_url — ссылка на видеофайл;
- created_at — время создания;
- updated_at — время изменения.

Данные фильмов хранятся в таблице movies в PostgreSQL.

Идентификаторы создаются PostgreSQL.
При обновлении backend изменяет updated_at.

Видео является внешним ресурсом:
в PostgreSQL хранится ссылка, сами медиаданные получает браузер.

### Служебные данные миграций

Таблица schema_migrations хранит названия применённых миграций
и время их выполнения.

Это техническая таблица, а не отдельная доменная сущность.

## 4. Реализация CRUD

### Create

POST /api/movies

Backend проверяет входные данные и создаёт запись в PostgreSQL.
При успехе возвращает HTTP 201 и созданный фильм.

### Read

GET /api/movies
GET /api/movies/{id}

Реализованы получение списка и отдельной записи.
Список поддерживает limit и offset.

### Update

PUT /api/movies/{id}

Запрос заменяет редактируемые поля существующего фильма.
При успехе возвращает HTTP 200 и обновлённую запись.

### Delete

DELETE /api/movies/{id}

Запрос удаляет фильм.
При успехе возвращает HTTP 204.

Для отсутствующей записи возвращается HTTP 404.

Все CRUD-операции доступны через frontend.

## 5. Соответствие методологии 12 факторов

### I. Codebase — единая кодовая база

Исходный код backend, frontend, миграций и конфигурации сборки
составляет один проект.

Предусмотрено хранение проекта в одном Git-репозитории.
Разные окружения должны развёртываться из версий этой кодовой базы.

Организационное условие соответствия:
проект необходимо инициализировать в Git и фиксировать изменения.
Одного наличия исходных файлов для выполнения фактора недостаточно.

### II. Dependencies — явные зависимости

Прямая зависимость от pgx объявлена в go.mod с конкретной версией.

Команда go mod tidy фиксирует необходимые косвенные зависимости
и создаёт go.sum с контрольными суммами модулей.
Оба файла должны входить в репозиторий и архив.

Dockerfile задаёт среду сборки.
Рабочий образ содержит собранный бинарный файл и сертификаты.

Frontend не использует внешние JavaScript-библиотеки.
Во время работы приложение не требует установленного компилятора
или дополнительных команд операционной системы.

Для строгой воспроизводимости контейнерного окружения
образы дополнительно фиксируются по digest:
даже версионный тег может быть перевыпущен.

### III. Config — конфигурация в окружении

Приложение получает настройки через переменные окружения:

- DATABASE_URL;
- PORT;
- LOG_LEVEL;
- DB_MAX_CONNS.

Пароль БД и адрес подключения не зашиты в исходный код.

.env.example содержит пример конфигурации.
Локальный .env исключён из Git и Docker build context.

Docker Compose передаёт значения процессу через environment.

Ссылки video_url являются данными отдельных фильмов,
поэтому хранятся в БД, а не в переменных окружения.

### IV. Backing services — внешние ресурсы

PostgreSQL используется как внешний сетевой ресурс.

Адрес и параметры доступа определяются DATABASE_URL.
Для подключения к другому совместимому экземпляру PostgreSQL
достаточно изменить конфигурацию и подготовить соответствующую БД.

Код приложения не зависит от локального пути хранения данных БД.

Источники видео также находятся вне процесса backend.

### V. Build, release, run — разделение этапов

Build:

Dockerfile загружает объявленные зависимости,
компилирует Go-код и встраивает frontend и миграции.
Результат — контейнерный образ.

Release:

Выбирается версия образа и конфигурация окружения.
Миграции выполняются отдельным процессом из выбранного образа.

Run:

HTTP-процесс запускается из готового образа.
При запуске зависимости не устанавливаются и код не компилируется.

Для соблюдения фактора опубликованные версии образов не должны
перезаписываться, а конфигурация релиза должна учитываться отдельно
от секретов в исходном коде.

### VI. Processes — процессы без постоянного локального состояния

Backend не хранит каталог в памяти, локальных JSON-файлах
или файловой системе контейнера.

Постоянные данные находятся в PostgreSQL.
Локальная память используется для обработки текущих запросов
и управления соединениями.

HTML, CSS и JavaScript внутри бинарного файла являются
неизменяемыми ресурсами сборки, а не пользовательским состоянием.

Перезапуск приложения не должен приводить к потере каталога.

### VII. Port binding — самостоятельный сетевой сервис

Go-приложение самостоятельно запускает HTTP-сервер
и слушает порт из переменной PORT.

Для работы не требуется встроенный в другой веб-сервер runtime.

Docker Compose публикует порт приложения для локального доступа.
В другом окружении этот порт может использовать балансировщик.

### VIII. Concurrency — масштабирование процессами

HTTP-процесс не содержит уникального постоянного состояния
и не требует привязки клиента к конкретной реплике.

Можно запустить несколько процессов приложения
с общей PostgreSQL и распределять запросы между ними.

Количество соединений одной реплики ограничивается DB_MAX_CONNS.

При масштабировании необходимо учитывать суммарное количество
соединений всех реплик и возможности PostgreSQL.

Текущий Compose запускает одну реплику и публикует фиксированный
порт на хосте. Для нескольких реплик потребуется изменить
публикацию портов и добавить балансировщик.

Архитектурная возможность предусмотрена;
испытание нескольких реплик не является результатом этой версии.

### IX. Disposability — быстрый запуск и корректная остановка

При старте процесс читает конфигурацию и проверяет соединение с БД.

Компиляция, загрузка зависимостей и миграции не выполняются
автоматически при запуске HTTP-сервера.

Приложение обрабатывает SIGINT и SIGTERM.

При штатной остановке сервер прекращает приём новых соединений
и ожидает завершения активных запросов до 10 секунд.

Compose предоставляет приложению 15 секунд на остановку.

Для сетевых операций и запросов к БД заданы таймауты.

При аварийном завершении уже подтверждённые записи остаются в БД.
Если соединение оборвалось до получения ответа на изменение,
клиенту необходимо проверить итоговое состояние:
гарантия однократного выполнения повторного POST не реализована.

### X. Dev/prod parity — близость окружений

Локально используется PostgreSQL, как и в предполагаемом
целевом окружении.

Не применяется замена PostgreSQL на SQLite или хранение в памяти.

Один Dockerfile формирует образ для разных окружений.
Различающиеся адреса, пароли и настройки передаются через окружение.

В целевом окружении следует сохранять совместимые версии БД
и использовать тот же проверенный образ приложения.

Production-окружение в рамках этой версии не развёрнуто.
Поэтому соответствие подтверждается устройством проекта
и рекомендуемым процессом развёртывания, а не сравнением
двух фактически работающих окружений.

### XI. Logs — журналы как поток событий

Приложение пишет структурированные JSON-логи в stdout.

Фиксируются:

- запуск и остановка сервера;
- выполнение миграций;
- HTTP-метод и путь;
- код ответа;
- длительность запроса;
- ошибки backend.

Приложение не создаёт файлы журналов
и не выполняет самостоятельную ротацию логов.

Сбор, хранение и ротацию должен обеспечивать слой окружения.

### XII. Admin processes — отдельные административные процессы

Миграции выполняются отдельной командой:

docker compose run --rm app migrate

Команда использует тот же контейнерный образ и настройки доступа
к БД, что и основной HTTP-процесс.

SQL-миграции поставляются вместе с приложением.

Применённые миграции учитываются в schema_migrations.
Транзакционная advisory-блокировка сериализует запуски мигратора.

Миграции не выполняются через публичный HTTP endpoint.

## 6. Проверка приложения

В проект включены модульные тесты валидации Movie.Input.

README.md содержит порядок ручной проверки:

1. Запуск PostgreSQL.
2. Выполнение миграций.
3. Запуск HTTP-приложения.
4. Проверка /healthz и /readyz.
5. Создание фильма.
6. Чтение списка и отдельной записи.
7. Изменение фильма.
8. Перезапуск контейнеров без удаления volume.
9. Проверка сохранности данных.
10. Удаление фильма.
11. Проверка HTTP 404 после удаления.
12. Проверка отклонения некорректных данных.
13. Проверка воспроизведения видео через frontend.

Перечисленные шаги являются планом проверки.
Фактические результаты необходимо зафиксировать после
самостоятельного запуска собранного проекта.

## 7. Ограничения

- Нет авторизации и разграничения прав.
- Не реализованы подписки и платежи.
- Нет загрузки и перекодирования видео.
- Нет адаптивного стриминга HLS/DASH.
- Видео зависит от доступности внешнего источника.
- Несколько реплик и балансировщик пока не развёрнуты.
- Нет автоматического отката миграций.
- Одновременные обновления одной записи используют
  правило последнего успешно выполненного обновления.

Эти ограничения определяют объём учебной версии.
Основные требования задания — frontend, backend,
PostgreSQL и CRUD — предусмотрены реализацией.
